# Deviations Log

Any deviation from the approved plan (`please-review-the-deliverables-studyplan-curried-hickey.md`)
must be recorded here with date, what changed, and why.

| Date | Component | Deviation | Reason |
|------|-----------|-----------|--------|
| 2026-07-03 | deps | numpy pinned 2.5.0 → 2.4.6 | numba 0.66 requires numpy<2.5; torch 2.11 still imports fine. No action needed. |
| 2026-07-03 | mccfr indexing | Plan said "flat offset arithmetic (street, seq_id, bucket)". Using an **open-addressed hash table** keyed by a 64-bit hash of the public betting state + bucket instead. | Dense `seq_id` requires enumerating the abstract betting tree. Measured sizes make this infeasible: 5.6M preflop action-SEQUENCES; even merging transpositions into public STATES gives 2.07M preflop states under the plan's original wide action menu. A dense seq_id map would itself be a multi-GB structure. Open addressing on a 64-bit state hash is the standard solution at this scale (Pluribus-style), is numba-friendly, and degrades gracefully. Collision analysis: ~460M keys in 2^64 → ~0.01 expected 64-bit collisions, so the hash IS the identity. |
| 2026-07-03 | infoset model | Indexing by resulting **public betting STATE** (imperfect recall of exact action order) rather than full action sequence (perfect recall). | Merges strategically-identical transpositions; standard sound abstraction (Waugh et al. imperfect recall). Cuts infosets by ~2.7x on the measured data. |
| 2026-07-03 | action abstraction (G6) | Plan's initial menu was fold/call/{0.5pot,1pot}/allin + 2.25bb preflop open, max 3 raises. **Narrowed to fold / call / pot-raise / all-in, max 2 raises per street, no separate preflop open.** | G6 memory gate. Measured per-street public-state counts and infoset totals (see README "G6 sizing"). The wide menu gave 11.2B infosets @5000 buckets = ~600GB, far over the 30GB budget. Chosen config gives ~461M infosets and ~26 GB. |
| 2026-07-03 | card buckets (G6) | Plan's initial target was flop/turn/river = 5000 each. **Set to 400 postflop buckets** (preflop stays 169 lossless). | Same G6 gate. Final measured config (fold/call/pot/allin, maxr2, no preflop open): 42232/272305/379757/382969 betting states/street → 421M infosets @400 buckets → ~27 GB hash table at 0.63 load. 5000 buckets would be ~11B infosets (~600 GB). 400 is the quality-vs-budget sweet spot; config-tunable to ~500 within 30 GB. |
| 2026-07-03 | mccfr discount_interval | Plan/config had `discount_interval=10000`. **Raised to 20,000,000.** | LCFR discounting scans the full 671M-slot table (~1.4s each). At 10k it fired ~every batch, cutting throughput 10x (188k→18k iters/s). At 20M it fires ~every 106s (~1.3% overhead) while preserving the linear-weighting benefit over the ~1e9-iter warmup. Verified via daemon throughput after the change. |
| 2026-07-03 | infoset table — race fix | Lock-free concurrent inserts created duplicate slots (measured **85% of used slots**; each infoset smeared over ~7 slots — no convergence possible, table overflow imminent). **Fix: single-threaded pre-population** of all reachable infosets (betting tree is finite: 1,077,263 states, cached in artifacts/betting_tree_v1.npz) before training; the training threads then only FIND, never insert. Also normalized slot_key to uint64 and auto-size capacity from the exact infoset count at 0.55 load. | Verified: 10M multithreaded iters → 0 new slots, 0 duplicates, 249,772 iters/sec (faster than the empty-table G5 number — duplicate flooding, not memory bandwidth, was the dominant slowdown). NOTE: this partially invalidates the earlier "memory-bound → cut to 100 buckets" reasoning; bucket count is re-decided by clean 15-min benchmarks (see BENCHMARK_PROTOCOL.md). Suffixed bucket sets for 100/200/400 built. |
| 2026-07-03 | buckets — web-reuse check | User asked to check for a freely downloadable equity/bucket artifact before building. **Verdict: build it ourselves.** | Searched. Downloadable *evaluators* are abundant (we use phevaluator; OMPEval/eval7/pokerkit/pokyr exist). Downloadable *precomputed abstractions* do NOT exist — every open project (Poker-MCCFRM, krukah/robopoker, pandaant/poker-cfrm) ships generator CODE, not artifacts (they're multi-GB and parameter-specific). This validates our approach: the standard method is OCHS (equity vs opponent clusters) for river + equity-distribution histograms with EMD k-means for turn/flop — exactly what we planned. robopoker needs 16 vCPU/120 GB for CPU clustering; our GPU (5090) path is faster and none of them use GPU. `pokyr` (OCHS/EHS2 C-extension) kept as an optional CPU cross-check only (needs a compiler; not a hard dep). |
